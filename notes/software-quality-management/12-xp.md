# 12-敏捷-XP（极限编程）

## 变更成本曲线

* 指数成本曲线：需求阶段一美元修好的 bug，到生产环境要花几千美元
  * **越往后改越贵**
* 传统的 SE：前期严谨，在早期做好一切
* 痛点：耦合 + 集成地狱 + 测试成本高

## XP 极限编程

* XP：快速响应需求变更，压平成本曲线
* 核心理念：**把有益的实践做到极致**，让改变不再昂贵
* 成本曲线拉平后的行为变化
  * 重大决策尽量晚做
  * 只实现当前必须实践的
  * 只在能简化当前代码时引入新设计
* 前提：**TDD + CI + 重构**

### 十项步骤

1. 寻找结对伙伴：领取任务卡（包含需求用例，如用户注册、登录）
2. 讨论任务：不确定就求助
3. 设计测试用例
4. 编写测试并让其失败：确认测试有效
5. 编写业务代码
6. 跑全部测试
7. 迭代测试与代码：增加下一个用例
8. 按需重构
9. 立即集成、测试
10. 领下一张任务卡

### 四条纪律

* 结对编程：一写一看，bug 即刻拦截
* 测试驱动：先写测试再写代码
* 结对不只是让测试通过：结对为分析、设计、实现、测试同时加值
* 即时集成

### 降低变更成本的技术

* 面向对象：修改局部化
* 简单设计
* 自动化测试
* 重构技术
* CI / CD

### 拉平成本的原因

* 严格执行 XP 实践，把反馈从几个月降低到几分钟
* 没有 XP 实践，就没有平坦曲线：不写测试、不持续集成的团队后期的后期改动同样痛苦

## 极限编程的实践

* 五大价值观：交流、简单、反馈、勇气、尊重
* 四项基本活动：编码、测试、倾听、设计

### 十二项基本实践

* 规划层
  * **计划游戏**：业务人员决定范围、优先级、发布组成、发布日期，技术人员决定估算、后果、流程、详细日程
  * **小发布**：每次发布应包含最有价值的业务需求
  * **现场客户**：真实用户必须与团队坐在一起，随时解答问题、解决争议
* 设计层
  * **隐喻**：使用隐喻取代架构，一致地命名类和方法，让团队保持同步
  * **简单设计**
  * **重构**：不应凭直觉重构
* 编码层
  * **TDD**：程序员：单元测试，客户：功能测试
  * **结对编程**：编码者负责战术视角，旁观者负责战略视角
  * **代码集体拥有制**：任何人若发现有机会为代码的任何部分增加价值，都随时去做
  * **编码标准**：统一编码标准是协作的前提
* 团队层
  * **持续集成**：在几小时内，最多一天完成集成与测试
  * **40 小时工作制**：加班是项目存在问题的信号

## TDD 和演进式设计

### TDD

### 四条测试纪律

* 独立：测试彼此之间独立
* 自动：测试不依赖于人工
* 即时：编码前完成测试
* 永存：测试代码永久保留，反复运行

### 五种测试类型

* 单元测试：程序员层面，测试单个类或方法
* 功能测试：客户层面，测试系统功能是否满足需求
* 并行测试：测试新旧系统行为一致
* 压力测试
* 随机测试：随机生成输入，测试系统的健壮性

### TDD 飞轮

* 红灯：编写一个失败的测试，仅定义接口和预期行为
* 绿灯：编写最少的代码使测试通过（允许硬编码）
* 增加测试：使用更多的测试样例，排除硬编码
* 重构：优化代码结构，保持测试通过

### 简单设计的四重准则

* 通过所有测试
* 消除重复
* 清晰表达意图
* 最小化元素数量

### 演进式设计

* 大前期设计：先用 UML 设计蓝图，再开始编码，灵活性低，让架构熵增
* Code-and-Fix：无约束，缺乏设计，难以维护
* **演进式设计**：XP 的设计理念，淡化大前期设计，采用简单设计 + 演进式运用设计模式
  * 生长式架构：杜绝超前开发，按需引入（YAGNI：You Ain't Gonna Need It）
  * UML 作为草图辅助，而非终稿
  * 降低流程中的不可逆性
    * 推迟决策时机
    * 增加可逆性：版本控制

## 持续集成

* 传统集成：周期长，易冲突，带来结构腐坏
* 持续集成 CI：团队成员频繁地（通常每天至少一次）将代码更改集成到共享的代码库主线中

### 集成的四步骤

1. 从主线拉取最新代码
2. 完成更改，在本地完整运行自动化构建
3. 推送前再次 pull 并构建
4. 推送到主线，触发中央的 CI 构建

### CI 的核心实践

* 显性：开发者
  * 维护单一主线代码库
  * 自动化构建
  * 自测试构建：构建包含测试 + 编译
  * 每人每天向主线提交
  * 每次提交都触发构建
  * 保持构建快速
* 隐性：平台层
  * 在类生成环境中测试
  * 任何人都能方便地获取最新的可执行文件
  * 每个人都能看到当前构建状态
  * 自动化部署

### 构建流水线

* 目的：提升反馈速度，保持开发者的心流
* 方法：将构建过程拆分为提交阶段、集成测试、端到端测试、性能 + 安全扫描
* 提交阶段在 10 分钟内完成

### 构建坏了的解决方法

* Revert 提交，并在 Revert 后的主线上修复
* 若情况紧急：在主线上快速修复并提交

### 隐藏未完成的功能

* Feature Toggle：配置开关，动态启用/禁用功能
* Branch by Abstraction：通过抽象层切换不同实现，隐藏未完成的功能
* Dark Launch：新功能部署到生产，但用户不可见

### CI/CD/持续部署

* CI 持续集成：自动完成构建、测试，手动部署
* CD 持续交付：CI + 自动部署到类生产环境，手动部署到生产环境
* Continuous Deployment 持续部署：CD + 自动部署到生产环境
* 三者逐层递进

### 其他

* Feature Branch & CI：若分支没有每天一次合并回主线，只能算自动化构建，不算 CI
* PR 和前置评审时间长，不利于快速反馈和 CI
  * 应对策略：结对编程、集成后评审、分类处理（重要变更重评审）、优化评审流程

## XP & Scrum

* Scrum 是容器，XP 是工程实践

| 维度    | XP             | Scrum    |
| ----- | -------------- | -------- |
| 迭代长度  | 1–2 周          | 2–4 周    |
| 迭代中变更 | 允许             | 不允许      |
| 任务顺序  | 严格按客户优先级       | 团队自决     |
| 工程实践  | 明确规定 TDD/CI/结对 | 不规定 留给团队 |
| 适用范围  | 仅软件开发          | 通用产品开发   |

## AI 时代的 XP

* CI：持续验证
* TDD：规格驱动开发
* 结对：人类 & AI & Reviewer 三方协作
