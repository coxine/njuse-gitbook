# 13-敏捷-精益软件开发&看板

## 精益软件开发

* 1950s 丰田生产系统：JIT、Jidoka
* 2003 Poppendick 提出同构映射

### 三大支柱

* JIT 准时化：按下游需求（用户故事）触发上游生产，消除库存与等待
* Jidoka 自働化：内建质量 + 赋予机器与员工"停止生产线"的权力（CI 红灯即停、单元测试失败即阻塞合并）
* WIP：库存，即系统中存在的物品数量，未合并的分支、待评审的 PR、堆积的工单都是隐形成本

### 七条规律

* 消除浪费：消除不为用户创造价值的活动
* 内建质量：TDD + CI + 结对编程，任何工具都有权停止生产线
* 创建知识
* 推迟决策：在信息最充分的时候做最优选择
* 快速交付：严格限制 WIP 的数量
* 尊重人
* 全局优化

## Kanban

* 通过可视化工作流程和限制 WIP 来实现持续流动
* 看板系统
  * 定义并可视化工作流程
  * 主动管理工作流程中的事项
  * 改进工作流程

### Kanban 六大实践

* 可视化
* 限制 WIP：每个阶段设置并发上限
* 管理流动
* 显式化策略
* 实施反馈循环
* 协同改进

### Kanban 度量

* WIP：已开始，但未完成的工作项数量
* 产能：单位时间内，团队完成的工作项数量
* 工作项存续时长：从工作项开始处理到当前的时间，针对未完成的任务
* 周期时间：从工作项开始处理到完成的时间，针对已完成的任务
* 平均 WIP = 产能 \* 平均周期时间（Little定律）

### Scrum & Kanban

| 特性    | Scrum                       | Kanban                         |
| ----- | --------------------------- | ------------------------------ |
| 框架性质  | 迭代式：通过固定长度的 Sprint 来规划和交付。  | 流动式：工作项持续流动，无固定迭代周期，可连续交付。     |
| 角色与责任 | 规定明确角色：PO、Scrum Master、开发团队 | 不规定必须角色：通常保留现有组织架构，鼓励团队自行分配任务。 |
| 时间规划  | 时间盒驱动：有固定的 Sprint 和一系列预设会议  | 事件驱动：没有 Sprint，会议按需举行          |
| 变更处理  | 不鼓励变更                       | 灵活变更                           |
| 核心度量  | 关注速度和燃尽图                    | 关注流程度量，如周期时间、吞吐量和在制品数量         |
| 适用场景  | 适合有明确交付节奏的项目                | 适合持续流动的工作，如运维支持、持续交付等          |

* Scrumban：保留 Scrum 部分结构（如定期会议），取消固定 Sprint 承诺，改用 Kanban 拉动节奏和 WIP 控制

### XP & Kanban

* XP：工程实践
* Kanban：流程管理，两者可兼容使用

### Agent 时代的 Kanban

* 瓶颈从编码转移到评审
* 两层 WIP：Agent 层（并行的 Agent 数量）+ 人类层（待审查的任务数量）
