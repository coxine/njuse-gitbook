# 13-软件架构模式

## 架构核心思想

| 架构       | 组织内容   | 核心思想                                                             |
| -------- | ------ | ---------------------------------------------------------------- |
| 主机/终端    | 核心事务   | 事务、数据、权限集中在主机，终端负责输入、显示                                          |
| C/S      | 交互能力   | 客户端承担 UI 和部分逻辑，服务器管理共享数据                                         |
| 三层/分层    | 职责边界   | 将表示层、业务层、数据层分离，降低系统耦合                                            |
| SOA      | 企业服务能力 | 不同系统通过服务契约暴露可复用能力，支撑跨系统整合                                        |
| 微服务      | 独立演进单元 | 围绕业务能力拆分服务，使团队、代码和发布边界对齐                                         |
| 事件驱动/云原生 | 运行时协作  | <p>事件驱动：生产者发布，消费者订阅并处理；<br>消息/流平台承担传递、缓冲、削峰与平台负责部署、扩缩容、恢复和观测</p> |

## 架构之间迁移的原因

* 主机/终端：交互能力弱，终端灵活性低
* C/S：客户端安装升级重，版本与兼容难治理
* 三层/分层：单系统可维护性提升，但跨系统复用不足
* SOA：企业级整合增强，但治理与总线成本较重，拖慢了迭代速度
* 微服务：局部发布更快，但分布式复杂度上升
* 事件/云原生：更适合高波动运行时，但时序与排障更难

## 架构对质量属性的影响

| 架构     | 优先保障的质量属性            | 相对牺牲的质量属性             |
| ------ | -------------------- | --------------------- |
| 主机/终端  | 一致性、安全性、可靠性、可审计性     | 易用性、交互响应性、局部修改灵活性     |
| C/S    | 易用性、响应性、桌面交互体验       | 可部署性、可维护性、版本一致性、统一治理  |
| 三层/分层  | 可维护性、可修改性、安全边界、部署治理  | 极致性能、跨系统复用、团队自治速度     |
| SOA    | 互操作性、可复用性、可组合性、可治理性  | 简单性、响应性能、轻量部署、局部演进速度  |
| 微服务    | 可部署性、可扩展性、可修改性、演进速度  | 强一致性、运维简单性、故障定位、全局理解  |
| 事件/云原生 | 弹性、韧性、可扩展性、可用性、自动化运维 | 可理解性、可调试性、时序可预测性、强一致性 |

## 结合具体业务系统说明

> 例：以选课系统为例，说明云原生架构可能存在的问题

* 选课请求和退课请求由不同的服务处理
* 用户 A 先提交了退课请求，再提交了选课请求，由于退课人数较多，选课请求先于退课请求被处理，导致用户 A 的选课请求被拒绝
* 云原生的松耦合，异步处理牺牲了时序可预测性和强一致性，导致了用户体验问题
